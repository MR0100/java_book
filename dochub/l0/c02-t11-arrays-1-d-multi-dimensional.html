Arrays (1-D, multi-dimensional)

An array is a fixed-size, indexed, contiguous block of same-typed elements. It's the only built-in aggregate in the Java language — every other data structure (ArrayList, HashMap, String, even StringBuilder's buffer) is implemented on top of arrays. Master arrays and you've mastered the memory shape under every container.

Arrays look simple — declare, allocate, index — but the depth is genuine. At the language layer, arrays have peculiarities found nowhere else: a length field (not a method!), covariance (Object[] o = new String[3] is legal and lets you blow up at runtime with ArrayStoreException), a literal syntax, and a parallel utility class (java.util.Arrays). At the bytecode layer, every element load and store has its own opcode family (iaload/iastore for int[], aaload/aastore for reference arrays, baload/bastore for byte[]/boolean[], etc.), every access carries an implicit bounds check (throws ArrayIndexOutOfBoundsException), and every reference store carries an implicit array-store check (throws ArrayStoreException). At the memory layer, an int[1_000_000] is ~4 MB contiguous in one allocation; an Integer[1_000_000] is ~20 MB scattered across 1,000,001 separate allocations — a 5× memory and ~10× cache penalty. At the architecture layer, the CPU's scaled-index addressing and stride-1 prefetcher make sequential primitive-array scans run at L1 throughput; the JIT's bounds-check elimination removes the per-access branch in idiomatic loops; row-major vs column-major access on a 2-D matrix changes performance by ~10× on large data. We'll cover every layer.

Why Arrays Exist — The Only Built-In Aggregate#

A variable holds one value (T02). An array holds N values of the same type, indexed 0..N-1. The two features that make arrays special and irreplaceable:

  1. Contiguous storage — all elements live in one allocation, adjacent in memory. The CPU's cache and prefetcher love this; primitive-array scans run at memory bandwidth.
  2. O(1) random access — arr[i] is one address calculation (base + i × sizeof(elem)) and one memory load. Constant-time regardless of i or array size.

Compare:

Structure Memory shape arr[i] cost
int[] contiguous; 4 bytes/elem O(1), one cache-line-friendly load
LinkedList<Integer> scattered nodes, each holds value + 2 pointers O(n) walk from head
ArrayList<Integer> contiguous backing Object[]; each elem is a heap Integer reference O(1) index, plus pointer-chase per elem
HashMap<Integer,X> hash table on contiguous Node[] buckets O(1) average via hash

Every "fast" structure in java.util is either an array internally (ArrayList, ArrayDeque, HashMap, PriorityQueue) or a tree of small arrays. Arrays are the foundation.

Declaring and Creating 1-D Arrays#

Declaration syntax#

The Java-idiomatic form puts the brackets on the type:

java
int[] nums;
String[] names;

A legacy C-style form puts brackets after the variable name:

java
int nums[];                  // legal but discouraged

Both produce identical compiled code; the modern style is int[] nums because it reads "an array-of-int named nums," matching how generics later read (List<Integer> nums). The legacy form is the inheritance from C/C++.

You can even mix on the same line — don't:

java
int[] a, b[];                 // a is int[]; b is int[][] — extremely confusing

Creation with new#

new <type>[size] allocates an array on the heap, zero-initialising every element to that type's default value:

java
int[] zeros = new int[5];      // {0, 0, 0, 0, 0}
double[] amounts = new double[3];   // {0.0, 0.0, 0.0}
boolean[] flags = new boolean[2];   // {false, false}
String[] words = new String[4];     // {null, null, null, null}
Element type Default value
byte, short, int, long 0
float, double 0.0
char '' (the NUL character)
boolean false
Any reference type null
flowchart TB New["new int[5]"] --> Alloc["allocate 16 bytes header + 5*4 bytes + padding"] Alloc --> Zero["zero every byte (JVM guarantee)"] Zero --> Ref["return reference to the array object"]

The zero-fill is a JVM guarantee — you never read garbage from a freshly-allocated array, unlike C. The JIT often implements the zero-fill via a rep stosb/memset-style instruction; for short arrays in stack-allocated escape-analyzed cases, it's a few xor + store instructions.

size may be any non-negative int. Negative size throws NegativeArraySizeException; larger than Integer.MAX_VALUE is a compile error (the size is an int); the practical maximum is also limited by the heap and by -XX:MaxArrayLength (~2³¹ - 8).

Array literals#

The literal syntax fills in elements directly. Two equivalent forms:

java
int[] primes = {2, 3, 5, 7, 11};                  // declaration form (short)
int[] primes2 = new int[]{2, 3, 5, 7, 11};         // expression form (long)

The short form is only legal at declaration — you can't reassign with it:

java
int[] primes;
primes = {2, 3, 5, 7, 11};                          // COMPILE ERROR
primes = new int[]{2, 3, 5, 7, 11};                  // OK — expression form

The expression form is what you need when passing a literal to a method:

java
System.out.println(Arrays.toString(new int[]{1, 2, 3}));     // OK
System.out.println(Arrays.toString({1, 2, 3}));               // COMPILE ERROR

Indexing — 0-based, half-open [0, length)#

arr[i] accesses the i-th element, with i ∈ [0, arr.length):

java
int[] arr = {10, 20, 30};
arr[0]              // 10
arr[2]              // 30
arr[3]              // throws ArrayIndexOutOfBoundsException
arr[-1]             // throws ArrayIndexOutOfBoundsException
flowchart LR I0["arr[0] = 10"] --- I1["arr[1] = 20"] --- I2["arr[2] = 30"] Idx["valid indices: 0 .. length-1 = 0 .. 2"]

The half-open convention [0, length) is the universal rule across Java APIs (substring, list slicing, stream ranges, IntStream.range). Once internalised it stops you from writing <= in for loop conditions (the off-by-one bug from T09).

The length field — field, not method#

Every array has a public final int field named length that holds the element count. You read it without parentheses:

java
int[] arr = new int[10];
arr.length          // 10
arr.length()        // COMPILE ERROR: 'length()' is not defined for int[]
⚠Warning

Arrays use arr.length (field). Strings use s.length() (method). Collections use c.size() (method). Three different idioms for "how many elements?" — get them straight or expect compile errors and code-review nits forever.

The field is immutable at the language level: there's no arr.length = 5 assignment, and the bytecode has no opcode for setting it. The length is decided at allocation and is fixed for the array's lifetime.

Array covariance and ArrayStoreException#

Java arrays are covariant: String[] is a subtype of Object[]. This lets you pass a String[] to a method expecting Object[]:

java
void printAll(Object[] arr) {
    for (Object o : arr) System.out.println(o);
}

String[] names = {"a", "b"};
printAll(names);                             // OK — covariance lets this through

The catch: you can store an Object into an Object[] at the language level. If the runtime array is actually a String[], the store fails:

java
Object[] arr = new String[3];                // covariance: String[] IS-A Object[]
arr[0] = "hello";                            // OK — string into string array
arr[1] = new Integer(42);                    // throws ArrayStoreException at runtime
flowchart TB Decl["Object[] arr = new String[3]"] Decl --> StoreCheck{"aastore: is value an instance of array's actual element type?"} StoreCheck -- yes --> Ok["store; OK"] StoreCheck -- no --> Throw["throw ArrayStoreException"]

Every reference-array store carries an implicit runtime type check — the aastore bytecode opcode performs it. The check costs ~1-2 extra cycles per store on hot paths and is the price of array covariance. It can't be eliminated by the JIT in general because the actual element type is only known at runtime.

This is why generics aren't covariant at the language level: List<String> is not List<Object>. Generics erasure means there's no runtime type to check against, so the language refuses the conversion at compile time instead. Arrays are the historical odd-one-out (pre-generics design from Java 1.0).

‼Important

Generic arrays don't fully exist. new T[10] is a compile error inside a generic class; new String[] is fine. You can have a T[] field if you cast from Object[], but it's the source of unchecked warnings. Prefer ArrayList<T> for generic collections.

Arrays.equals vs arr.equals#

arr.equals(arr2) is reference equality — inherited from Object.equals — and only returns true if both references point to the same array object:

java
int[] a = {1, 2, 3};
int[] b = {1, 2, 3};
a.equals(b)                  // false — different array objects
Arrays.equals(a, b)          // true — element-wise comparison
⚠Warning

Always use Arrays.equals(a, b) for value comparison; a.equals(b) on arrays is almost always a bug. (Some lint tools catch it; most don't.)

Arrays.asList(...) — the two traps#

Arrays.asList returns a fixed-size List<T> backed by the input array. Adding or removing elements throws UnsupportedOperationException:

java
List<String> names = Arrays.asList("a", "b", "c");
names.set(0, "z");                           // OK — same array, slot 0 replaced
names.add("d");                              // throws UnsupportedOperationException

The first trap is autoboxing-blind: Arrays.asList(int[]) does not give you a List<Integer>:

java
int[] arr = {1, 2, 3};
List<int[]> wrapped = Arrays.asList(arr);     // length 1! the int[] is a SINGLE element
wrapped.size()                                 // 1

This is because Arrays.asList is varargs <T> List<T> asList(T... a). T cannot be a primitive; it can be int[]. So a single int[] argument is treated as one element of type int[], not as N Integer elements. Use IntStream.of(arr).boxed().toList() (Java 16+) or Arrays.stream(arr).boxed().toList().

Second trap: a boxed wrapper array does what you'd expect:

java
Integer[] boxed = {1, 2, 3};
List<Integer> list = Arrays.asList(boxed);    // size 3 — varargs expands the array

But you've already paid the autoboxing cost to build the Integer[] in the first place.

System.arraycopy — bulk copy#

For copying ranges between arrays, System.arraycopy(src, srcPos, dst, dstPos, length) is the canonical primitive:

java
int[] src = {1, 2, 3, 4, 5};
int[] dst = new int[5];
System.arraycopy(src, 1, dst, 0, 3);          // dst = {2, 3, 4, 0, 0}

It's a native HotSpot intrinsic — lowers to rep movsb (Intel ERMS) or movdqu-loop on x86-64, and to ldp.q/stp.q 32-byte-pair loops on ARM64. It runs at memory bandwidth (T07's arraycopy deep dive).

Arrays.copyOf and Arrays.copyOfRange are convenience wrappers that allocate the destination first:

java
int[] grown = Arrays.copyOf(arr, arr.length * 2);    // alloc + arraycopy + zero-pad
int[] slice = Arrays.copyOfRange(arr, 2, 5);          // alloc + arraycopy

clone() — shallow copy#

Every array has a clone() method (inherited from Object, with a covariant return type so int[].clone() returns int[]):

java
int[] a = {1, 2, 3};
int[] b = a.clone();                          // {1, 2, 3} — independent copy
b[0] = 99;
System.out.println(a[0]);                     // 1 — a is unaffected

For a 1-D primitive array clone() is exactly the same as Arrays.copyOf(a, a.length) — a single arraycopy of the elements.

For a 1-D reference array clone() copies the references (not the referenced objects):

java
String[] words = {"a", "b"};
String[] words2 = words.clone();              // words2 holds the same two String refs

For a multi-D array clone() is shallow: it copies the outer array, but the inner sub-arrays are shared between the original and the clone:

java
int[][] grid = {{1,2},{3,4}};
int[][] copy = grid.clone();                  // outer array cloned; inner arrays SHARED
copy[0][0] = 99;
System.out.println(grid[0][0]);              // 99 — the inner int[] is shared!
flowchart TB G["grid (int[][]) — outer array"] --> R1G["row 0: int[2] {1,2}"] G --> R2G["row 1: int[2] {3,4}"] C["copy (int[][]) — outer cloned"] --> R1G C --> R2G Note["clone() copies only the outer references — inner arrays are SHARED"]

For a true deep copy of a 2-D array, clone each row individually:

java
int[][] deep = new int[grid.length][];
for (int i = 0; i < grid.length; i++) deep[i] = grid[i].clone();

Multi-Dimensional Arrays — "Arrays of Arrays"#

Java has no true multi-dimensional array. int[][] is an int[] whose elements are themselves int[] references. The C/Fortran "one contiguous block of R*C ints" doesn't exist as a language construct (you can simulate it with int[r*c] and manual indexing — covered below).

Declaration and creation#

java
int[][] grid = new int[3][4];                 // 3 rows, 4 columns, rectangular

This is two-step allocation under the hood:

  1. Allocate the outer int[][] of length 3 (12-byte header + 4 byte length + 3 × 4-byte refs + padding = 32 bytes).
  2. For each of the 3 outer slots, allocate a fresh inner int[4] (16 + 16 + 0 padding = 32 bytes each) and store its reference.

Result: 4 allocations (one outer + three inner), non-contiguous memory layout, each row independently sized.

flowchart TB Outer["outer int[][] (length 3)"] Outer --> R0["int[4] {0,0,0,0}"] Outer --> R1["int[4] {0,0,0,0}"] Outer --> R2["int[4] {0,0,0,0}"] Note["four separate heap allocations; rows may be far apart in memory"]

The "only outer" form for jagged arrays#

You can create the outer array and leave the inner rows null, then fill them with arrays of different lengths:

java
int[][] jagged = new int[3][];                // outer alloc only; rows are null
jagged[0] = new int[]{1};
jagged[1] = new int[]{1, 2};
jagged[2] = new int[]{1, 2, 3};
flowchart TB J["jagged (length 3)"] J --> JR0["int[1] {1}"] J --> JR1["int[2] {1,2}"] J --> JR2["int[3] {1,2,3}"]

Jagged arrays are useful when row lengths genuinely vary (e.g. a list of edges per vertex in a graph). They have the same byte cost as the rectangular form for the same total element count.

Multi-D literal#

java
int[][] grid = {
    {1, 2, 3},
    {4, 5, 6},
    {7, 8, 9}
};

Same shape as the new int[3][3] form, populated. Inner braces are themselves array literals.

Indexing#

grid[r][c] is two indexed loads: first grid[r] to get the inner array reference (via aaload), then inner[c] to get the int element (via iaload).

flowchart LR Source["grid[r][c]"] --> Load1["aaload: outer[r] -> int[]"] Load1 --> Load2["iaload: inner[c] -> int"]

Two memory loads per access — vs one for a flat int[r * cols + c]. The JIT will inline both, but the cache footprint of multi-D is meaningfully larger.

Row-major iteration is cache-friendly#

java
for (int r = 0; r < grid.length; r++) {
    for (int c = 0; c < grid[r].length; c++) {
        sum += grid[r][c];
    }
}

The inner loop walks one row sequentially — within a row, the ints are contiguous (each row is its own contiguous int[]), and the prefetcher streams them into L1. Good.

Column-major iteration is cache-hostile on large matrices#

java
for (int c = 0; c < grid[0].length; c++) {
    for (int r = 0; r < grid.length; r++) {
        sum += grid[r][c];
    }
}

Each grid[r][c] is in a different row's int[] — potentially a different cache line on every access. For a 1000×1000 int[][], the rows are likely 4 MB apart and column-major iteration misses L1 on every access.

flowchart TB RowMajor["row-major: arr[0][0], arr[0][1], arr[0][2], ... — one row, sequential"] RowMajor --> Cache1["all in same cache line; prefetcher streams"] ColMajor["column-major: arr[0][0], arr[1][0], arr[2][0], ... — different rows"] ColMajor --> Cache2["each access a different row's array; cold cache hits"]

We'll quantify this in the architecture section. The rule of thumb: iterate the rightmost (innermost) index in the inner loop.

Flat int[r * c] for performance-critical 2-D#

When you need maximum performance on a rectangular 2-D, flatten it:

java
int rows = 1000, cols = 1000;
int[] flat = new int[rows * cols];
int get(int r, int c) { return flat[r * cols + c]; }
void set(int r, int c, int v) { flat[r * cols + c] = v; }

Trade-offs:

  • One allocation instead of rows + 1.
  • One contiguous block — best possible cache behaviour.
  • One indexed load instead of two.
  • The r * cols + c computation, which the JIT can simplify (induction variable in a for (r) for (c) ... r * cols + c becomes a running counter).
  • Loses the "jagged" capability.
  • Loses grid[r].length — you must track rows and cols separately.

For dense numerical work (matrices, image buffers, neural-net tensors), the flat form is universal. For sparse or jagged data, the array-of-arrays form is right.

Three and more dimensions#

java
int[][][] cube = new int[3][4][5];            // 3 layers × 4 rows × 5 cols

Same recursive idea — an int[3][4][5] is an int[][][] of length 3, each element an int[][] of length 4, each element an int[5]. The compiler emits a single multianewarray bytecode opcode for rectangular multi-D creation; it allocates all the layers in one call.

Memory Layer — Byte-Level Array Layout#

The Array Object Header#

Every Java array is a heap-allocated object with an extended object header. The standard layout on a 64-bit HotSpot with compressed oops (the modern default):

offset 0  +-----------------------------+
          | mark word (8 bytes)         |  <- GC bits, hash, lock state
offset 8  +-----------------------------+
          | klass pointer (4 bytes,     |  <- compressed oops; 8 bytes without
          |  compressed)                |
offset 12 +-----------------------------+
          | length (4 bytes, int)       |  <- the .length field
offset 16 +-----------------------------+
          | element 0                   |
          | element 1                   |
          | ...                         |
          | element N-1                 |
          +-----------------------------+
          | padding to 8-byte alignment |
          +-----------------------------+

So the fixed overhead per array is 16 bytes (12 header + 4 length, aligned to 8). The element area is N * sizeof(elemtype), rounded up to the next 8-byte boundary.

Per-type element sizes#

Element type Bytes per element int[10] total T[10] total (compressed oops)

byte 1 32 —
short, char 2 16 + 20 + 4 pad = 40 —
int, float 4 16 + 40 + 0 pad = 56 —
long, double 8 16 + 80 + 0 pad = 96 —
reference (compressed) 4 — 16 + 40 + 0 pad = 56

‼Important

boolean[] is not a bit-array. Each boolean occupies 1 full byte in HotSpot — for memory-density-critical bitmaps, use BitSet or a long[] with manual bit-shifting.

int[1_000_000] vs Integer[1_000_000]#

int[1_000_000]:
  16 (header + length) + 4_000_000 (elements) + 0 pad
  = ~4 MB, ONE allocation, contiguous

Integer[1_000_000]:
  16 (header + length) + 4_000_000 (references, compressed) + 0 pad
  = 4 MB for the array itself
  + 1_000_000 × 16 (each Integer: 12 hdr + 4 value + 0 pad = 16 bytes)
  = + 16 MB for the Integer objects, SCATTERED across the heap
  = ~20 MB total, 1_000_001 allocations

5× memory and roughly 10× worse cache behaviour. This is why every performance-sensitive Java codebase uses primitive arrays over wrapper arrays where it can.

Element-load and element-store opcodes — per-type#

The JVM has a dedicated opcode per element type for array reads and writes. The naming pattern is <type>aload for reads and <type>astore for writes:

Bytecode Element type read/written Reads stack Pushes/pops
iaload / iastore int (and byte, short, char after auto-promote) int[], int (index) int / pops int value
laload / lastore long long[], int long
faload / fastore float float[], int float
daload / dastore double double[], int double
aaload / aastore reference (any object) Object[], int reference
baload / bastore boolean or byte byte[]/boolean[], int int
caload / castore char char[], int int
saload / sastore short short[], int int

Plus three array-administration opcodes:

Bytecode Role
newarray allocate a primitive array (new int[size], new boolean[size], etc.)
anewarray allocate a reference array (new String[size])
multianewarray allocate a rectangular multi-D array (new int[3][4][5])
arraylength read arr.length — single opcode

Each load/store reads the array reference and the index from the operand stack, performs the access, and (for loads) pushes the element. Each access carries an implicit check:

  1. Null check: if the array reference is null, throw NullPointerException.
  2. Bounds check: if the index is < 0 or >= length, throw ArrayIndexOutOfBoundsException.
  3. Store check (aastore only): if storing a reference, verify it's assignable to the array's actual element type; if not, throw ArrayStoreException.
flowchart TB Op["iaload"] --> Null{"arr == null?"} Null -- yes --> NPE["throw NPE"] Null -- no --> Bounds{"0 <= idx < length?"} Bounds -- no --> AIOOBE["throw ArrayIndexOutOfBoundsException"] Bounds -- yes --> Load["push arr[idx] to stack"]

The bounds check is what range-check elimination (T09) targets — when the JIT proves the loop invariant 0 ≤ i < length, it omits the check.

Worked javap -c for a 1-D scan#

Source:

java
int sum(int[] arr) {
    int s = 0;
    for (int i = 0; i < arr.length; i++) s += arr[i];
    return s;
}

Bytecode:

 1: istore_2                    // s = 0
 2: iconst_0

 4: iload_3                     // load i
 5: aload_1                     // load arr
 6: arraylength                  // arr.length
 7: if_icmpge   23              // i >= arr.length? exit

11: aload_1                     // load arr
12: iload_3                     // load i

Every iteration: one arraylength (often hoisted by the JIT via LICM — T09), one iaload (with implicit bounds check, eliminated by RCE — T09), one iinc, one if_icmpge, one goto. After JIT: ~3 native instructions per element, often 8 elements per AVX2 SIMD instruction.

Worked javap for a 2-D scan — two-level indexing#

Source:

java
int sumGrid(int[][] grid) {
    int s = 0;
    for (int r = 0; r < grid.length; r++) {
        for (int c = 0; c < grid[r].length; c++) {
            s += grid[r][c];
        }
    }
    return s;
}

Bytecode for the inner-body element load:

... (inner loop body) ...
   aload_1               // load grid
   iload_3               // load r
   aaload                // grid[r] : int[]
   iload   4             // load c
   iaload                // (int[])[c] : int
   iadd                  // s += ...
   ...

Two indexed loads per element. The aaload reads a reference (the inner int[]); the iaload reads the int. Both carry their bounds checks; the JIT can eliminate both if the loop bounds use the same .length fields.

Multi-D allocation — multianewarray#

For new int[3][4], javac emits a single bytecode:

   iconst_3
   iconst_4
   multianewarray   [[I, 2     // type descriptor "[[I" (int[][]), dimensions count 2

This one opcode does all four allocations (one outer + three inner) and links them together. For new int[3][] (outer only), javac emits anewarray [I instead — one allocation, inner slots null.

Lifetime and GC#

An array is a regular heap object: it stays alive as long as some reachable reference holds it; the GC reclaims it when nothing references it. A multi-D array's inner sub-arrays are referenced by the outer array, so they stay alive as long as the outer does — until you null out a slot:

java
int[][] grid = new int[1000][1000];           // ~4 MB total
grid[0] = null;                                // row 0's int[1000] becomes garbage
// ~4 KB freed at next GC

For very large arrays you may want to consider -XX:+UseG1GC or -XX:+UseZGC (the latter handles multi-GB arrays without long pauses); the default G1 already handles arrays well up to many GB.

Architecture Layer — CPU, Cache, JIT#

Scaled-index addressing — array access is free address math#

x86-64 and ARM64 both have scaled-index addressing modes that compute base + index × scale in the address-generation unit, in parallel with the ALU. So arr[i] for an int[] (scale=4) is:

asm
; x86-64 (rdx = arr_base, rdi = i)
mov     eax, [rdx + rdi*4]              ; one instruction; *4 is free
asm
; ARM64 (x3 = arr_base, w0 = i)
ldr     w4, [x3, w0, sxtw #2]           ; one instruction; #2 = log2(4), sxtw promotes
flowchart TB Src["arr[i] (int[])"] --> X86["x86-64: mov eax, [rdx + rdi*4]"] Src --> ARM["ARM64: ldr w4, [x3, w0, sxtw #2]"] Note["the *4 and sxtw #2 are free — computed in the address unit"]

For long[] use scale 8; for byte[] use scale 1; for double[] use 8. The CPU handles all of them. The *sizeof(elem) is invisible to the throughput count — it's not a multiply, it's a shift inside the load unit.

Bounds-Check Elimination (recap from T09)#

The naive lowering of arr[i] would emit:

asm
        cmp     edi, [rdx - 4]          ; arr.length sits 4 bytes before element 0
        jae     .throw_aioobe           ; >= length unsigned -> throw
        mov     eax, [rdx + rdi*4]      ; safe to access

The JIT proves 0 ≤ i < arr.length for idiomatic for (int i = 0; i < arr.length; i++) and deletes the cmp + jae entirely. The loop body becomes a single load. This is the difference between Java being competitive with C on numeric loops vs being 3-5× slower.

Cache lines and the prefetcher#

A modern x86-64 CPU has 64-byte L1 cache lines — 16 ints, 8 longs, 8 doubles, or 32 shorts per line. When you read arr[0], the cache pulls in arr[0..15] for free. When you read arr[1], it's already there.

The hardware prefetcher detects stride-1 access after ~3-4 misses and starts loading future cache lines speculatively. By the time the loop iterates past element 15 of the first line, the line containing arr[16..31] is already arriving in L1.

flowchart TB Iter1["read arr[0..15] — line N"] Iter1 -.-> Prefetch["prefetcher: 'stride-1 detected; fetch line N+1, N+2'"] Iter2["read arr[16..31] — line N+1 (already in L1)"] Iter2 -.-> PF2["prefetcher: continue fetching N+3, N+4"]

Result: sequential primitive-array scans run at L1 throughput (~4 ints/cycle on Skylake-era), which is many times faster than DRAM bandwidth would permit if you missed L1 on every access.

int[] vs Integer[] — the cache disaster#

Walk int[1_000_000] sequentially: 1,000,000 / 16 = 62,500 cache lines, all stride-1, all prefetcher-friendly.

Walk Integer[1_000_000] sequentially: 62,500 lines for the reference array, but each reference points to a separate 16-byte Integer object somewhere in the heap. The prefetcher cannot follow pointers (it only knows strides), so each Integer access is a cold cache load — potentially ~100 ns to L3, ~300 ns to DRAM. 1,000,000 cold cache misses for the loop body, vs ~62,500 warm hits for int[].

For a sum loop, this is the difference between ~1 ms (int[]) and ~50–100 ms (Integer[]) on the same hardware. 50–100×.

Row-major vs column-major — the 2-D matrix case#

For a 1000×1000 int[][]:

  • Row-major (for r: for c: grid[r][c]): inner loop walks one row's int[1000] sequentially. Each row is contiguous; prefetcher streams. 1000 cache-warm rows × 1000 iterations = 1 ms total.
  • Column-major (for c: for r: grid[r][c]): each access reads a different row's int[]. The 1000 rows are scattered across ~4 MB of heap. Each access is potentially a cache miss to L2 or L3. ~10–50 ms total.
flowchart TB RM["row-major: 1000 rows × 1000 sequential reads = ~1 ms"] CM["col-major: 1,000,000 scattered reads = ~10-50 ms"] Bench["benchmarked difference: ~10x"] RM --- vs --- CM vs --> Bench

Iterate the rightmost index in the innermost loop. That's the universal rule for cache-friendly multi-D loops in any row-major language (Java, C, Rust, Go). Fortran and MATLAB are column-major, so the rule inverts there.

Arrays.sort — two different algorithms#

Arrays.sort is overloaded per element type, and the algorithm differs:

  • Arrays.sort(int[]) (and long[], float[], double[], char[], short[], byte[]) uses dual-pivot quicksort (Yaroslavskiy's variant, 2009). In-place, O(n log n) average, O(n²) worst case (rare with three-way partition); faster than classical Hoare quicksort by ~20% on random data because the dual pivots reduce comparisons.
  • Arrays.sort(Object[]) (and Arrays.sort(List), Collections.sort) uses Timsort (Tim Peters, 2002 — same as Python's sorted). Stable (equal elements keep their original order), O(n log n) worst case, exploits pre-existing sorted runs, allocates a temp array (O(n) extra space).

Why the split? Primitive arrays don't have equal-but-distinguishable elements, so stability is meaningless; quicksort's in-place nature wins. Object arrays often have stability requirements (sort by name, preserve original order for equal names) and may already be partially sorted (Timsort exploits this).

flowchart TB Sort["Arrays.sort"] --> Prim["primitive arr -> dual-pivot quicksort (in-place, O(n log n) avg)"] Sort --> Obj["Object arr -> Timsort (stable, O(n log n) worst, O(n) extra space)"]

Arrays.parallelSort(...) uses a parallel merge-sort based on the fork/join framework — splits the array, sorts pieces on different threads, merges. Wall-clock improvement on large arrays (~4 cores → ~3× faster on 1M elements); not worth the overhead for small arrays (the JDK uses a small-input threshold).

System.arraycopy as a HotSpot intrinsic#

System.arraycopy(src, sp, dst, dp, len) is not a regular Java method call. HotSpot intercepts it and emits native bulk-copy code:

  • x86-64: rep movsb (Intel ERMS-optimised) or an AVX2 unrolled loop using vmovdqu 32-byte loads/stores. Runs at L1 cache bandwidth for in-cache data, memory bandwidth for out-of-cache.
  • ARM64: paired ldp.q/stp.q (32-byte loads/stores) in an unrolled loop, or dc zva (data-cache zero-by-VA) when zeroing.

A 1 GB copy on modern hardware takes ~100 ms (~10 GB/s memory bandwidth). No Java loop you write by hand will match this — always use System.arraycopy for bulk copy.

flowchart TB Call["System.arraycopy(src, sp, dst, dp, len)"] Call --> HotSpot["HotSpot intrinsic: skip the Java call"] HotSpot --> Native["emit rep movsb / vmovdqu loop (x86) or ldp.q (ARM)"] Native --> MB["~memory bandwidth (~10 GB/s)"]

False sharing on parallel array writes#

When multiple threads write to different slots of the same array in adjacent cache lines, the CPU treats it as one shared line and bounces ownership between cores — false sharing. Each write is delayed by tens to hundreds of cycles. For int[] shared across threads:

java
int[] counters = new int[NUM_THREADS];      // each thread writes its own slot

— disastrous: all 16 slots fit in one 64-byte line, and the line ping-pongs between cores. Fix by padding each counter to its own cache line, or using LongAdder (which handles striping internally). Full coverage in L3/C01 (concurrency).

Escape Analysis on short-lived arrays#

int[] temp = new int[16] inside a method that doesn't pass temp to an un-inlined caller: HotSpot's scalar replacement can lift the array elements into stack-allocated slots or registers, eliminating the heap allocation entirely. This is the same EA mechanism we saw for StringBuilder (T07) and Iterator (T09). For small, bounded, non-escaping arrays it works; for arrays of unbounded or runtime-determined size it usually doesn't.

Common Mistakes#

⚠Warning

The classic array bug catalogue. These come up in code review constantly.

arr.length vs arr.length()#

arr.length is a field. Writing arr.length() is a compile error specific to arrays — Strings have .length(), collections have .size(), arrays have .length. Memorise the three.

0-based vs 1-based off-by-one#

java
for (int i = 1; i <= arr.length; i++) arr[i] = ...;     // both ends off by one!

The right form is for (int i = 0; i < arr.length; i++). The half-open [0, length) convention is universal in Java APIs.

arr.equals(arr2) is reference equality#

java
int[] a = {1, 2, 3};
int[] b = {1, 2, 3};
a.equals(b)              // false! reference equality
Arrays.equals(a, b)       // true

Object.equals defaults to ==; arrays don't override it. Always use Arrays.equals or Arrays.deepEquals.

Arrays.asList(int[]) returns a List<int[]> of size 1#

java
int[] arr = {1, 2, 3};
List<int[]> wrong = Arrays.asList(arr);     // size 1!

Varargs <T> cannot bind to a primitive type. Use IntStream.of(arr).boxed().toList() to get a List<Integer>.

Shallow clone() on 2-D arrays#

Covered earlier — grid.clone() shares inner rows. For a real deep copy of a T[][], clone every inner row. For a T[][][], recursively.

Modifying an array after passing to a method#

Pass-by-value-of-reference (T02): a method receives a copy of the reference, not a copy of the array. Mutations inside the method are visible to the caller.

java
void zero(int[] arr) { for (int i = 0; i < arr.length; i++) arr[i] = 0; }

int[] data = {1, 2, 3};
zero(data);
// data is now {0, 0, 0}

This is correct Java — but readers from Python or JS may expect "by value" semantics. Defensive copy (int[] safe = arr.clone()) if you don't want callees mutating.

ArrayStoreException from generic-array confusion#

java
Object[] arr = new String[3];
arr[0] = 42;                              // throws ArrayStoreException

Array covariance + reference-type stores. The runtime check fires. Use generics (List<String>) for type-safe collections.

Allocating in a hot loop#

java
for (int i = 0; i < n; i++) {
    int[] temp = new int[16];             // allocates every iteration!
    process(temp);
}

Hoist the allocation out of the loop, or reuse with Arrays.fill(temp, 0) if the contents don't need to outlive the loop. The JIT's EA may eliminate this if temp doesn't escape, but don't rely on it.

int[] to List<Integer> autoboxing cost#

java
int[] arr = {1, 2, 3, ..., 1_000_000};
List<Integer> list = Arrays.stream(arr).boxed().collect(Collectors.toList());

5× memory blow-up plus 1 million allocations. Stay in int[] (or IntStream) if you can; box only at the boundary where you need List<Integer>.

Forgetting that an Object[] may not be what its declared type says#

java
String[] names = new String[3];
Object[] o = names;
o[0] = new Integer(42);                  // throws ArrayStoreException

Covered above — Object[] o doesn't mean "an array that holds anything"; it means "a reference to some array, whose actual element type is determined at allocation time."

Multi-D arrays "must" be rectangular#

False — int[3][] is legal and leaves rows null for you to fill with different lengths (jagged). Only the rectangular form int[3][4] allocates all rows up front.

Arrays.copyOf truncation vs extension#

java
int[] a = {1, 2, 3};
int[] b = Arrays.copyOf(a, 5);            // {1, 2, 3, 0, 0}  — padded with default
int[] c = Arrays.copyOf(a, 2);            // {1, 2}           — truncated

The behaviour is "exactly newLen elements; pad or truncate the source." Useful when growing an ArrayList-style buffer (Arrays.copyOf(arr, arr.length * 2)).

🎤Interview

Arrays are a perennial Java interview topic. Common angles:

  1. What's the difference between arr.length and arr.length()? Arrays have a length field; Strings have a length() method; collections have size().
  2. Why is Arrays.asList(int[]) size 1? Varargs can't bind T to a primitive; it binds T = int[], treating the whole array as one element. Use IntStream.of(...).boxed().toList().
  3. What's array covariance? T[] is a subtype of S[] if T extends S. Lets you pass String[] to Object[] params. Cost: runtime ArrayStoreException on incompatible reference stores.
  4. Why aren't generics covariant? Erasure — no runtime element type to check; the language enforces invariance at compile time instead.
  5. How is int[][] laid out in memory? Outer int[][] of references + N separately-allocated inner int[]s. Non-contiguous; row-major iteration is cache-friendly.
  6. What's the byte size of int[10]? 16 (header + length) + 40 (elements) + 0 padding = 56 bytes.
  7. What's the byte size of Integer[10]? 16 + 40 (refs) + ... + ~160 (10 Integers) = ~200 bytes scattered (depending on cache).
  8. What's iaload and what does it cost? Bytecode for int[] element read. Implicit null + bounds check. JIT eliminates the bounds check in idiomatic loops (RCE).
  9. Which sort does Arrays.sort(int[]) use? Dual-pivot quicksort (Yaroslavskiy), in-place, O(n log n) avg.
  10. Which sort does Arrays.sort(Object[]) use? Timsort. Stable. O(n log n) worst.
  11. How fast is System.arraycopy? HotSpot intrinsic; runs at memory bandwidth (rep movsb / vmovdqu on x86; ldp.q on ARM).
  12. Why is int[] 50× faster than Integer[] in a tight sum loop? Cache packing + prefetcher: int[] is contiguous (16/line, stride-1); Integer[] is pointer-per-element with scattered boxes (cold miss per element).

Practice#

  1. JOL layout dump. Use the Java Object Layout (JOL) library to print int[10], Integer[10], and Object[10] layouts. Confirm 16-byte header + 4×N elements + padding.
  2. int[] vs Integer[] memory. Measure heap before and after allocating int[1_000_000] and Integer[1_000_000] (with all Integer values created via new Integer(i) to disable caching). Confirm ~4 MB vs ~20 MB.
  3. int[] vs Integer[] performance. Sum 100M elements both ways. Measure nanos. Confirm 30–50× difference.
  4. Row-major vs column-major. Sum a 2000×2000 int[][] row-major then column-major. Measure. Confirm ~10× difference.
  5. Flat array as 2-D. Reimplement the same matrix sum using int[2000*2000] and idx = r*cols + c. Measure. Should be ~as fast as row-major int[][] (maybe slightly faster due to one fewer indirection).
  6. javap -c 1-D sum. Disassemble the sum loop. Find arraylength, iaload, iinc, the backward goto.
  7. javap -c 2-D access. Disassemble grid[r][c]. Find the aaload followed by iaload.
  8. javap -c multi-D creation. Disassemble new int[3][4]. Find the multianewarray opcode.
  9. Range-check elimination. Run for (int i = 0; i < arr.length; i++) arr[i] = i; with -XX:+PrintAssembly (needs hsdis). Confirm no cmp arr_length, idx bounds check inside the inner loop. Then rewrite as for (int i = 0; i < computeLen(arr); i++) where computeLen is in another class; observe the check re-appearing.
  10. ArrayStoreException reproduction. Reproduce the Object[] o = new String[3]; o[0] = 42; example. Trace the JVM error message; identify the array's actual element type.
  11. Shallow clone() 2-D trap. Clone a 2-D int[][]. Modify a deeply-nested element. Confirm the original sees the change. Fix with per-row clone.
  12. Arrays.asList(int[]) trap. Reproduce the size() == 1 confusion. Compare to Arrays.asList(Integer[]) (size N) and Arrays.asList(1, 2, 3) (size 3).
  13. Arrays.sort algorithm observation. Sort an int[1M] and an Integer[1M] with random data. Measure. Sort a partially-sorted Integer[]. Confirm Timsort exploits the runs (much faster than random); dual-pivot doesn't get the same speedup on partially-sorted int[].
  14. System.arraycopy intrinsic. Run -XX:+PrintIntrinsics. Run a loop that does System.arraycopy. Confirm it's intrinsified. Then write a manual copy loop; benchmark; observe the manual loop is significantly slower (no SIMD/ERMS).
  15. Auto-vectorisation on int[]. Sum int[1M] with -XX:+PrintAssembly. Find vpaddd (AVX2) or add v.4s (NEON). Switch off with -XX:-UseSuperWord; measure throughput drop.
  16. boolean[] byte cost. Allocate boolean[1_000_000]; measure heap. Confirm it's ~1 MB (one byte per bool), not ~128 KB (one bit per bool). Compare to BitSet.
  17. Explain it back. Trace int[][] g = new int[3][4]; g[1][2] = 42; from source through (a) multianewarray bytecode, (b) the four heap allocations, (c) the aaload + iastore for the assignment, (d) the JIT's two scaled-index movs, (e) the cache-line(s) touched.

  • Recognise an array as Java's only built-in aggregate: fixed-size, contiguous, indexed, O(1) random access, the foundation under every container in java.util.

# Arrays (1-D, multi-dimensional)

An **array** is a fixed-size, indexed, contiguous block of same-typed elements. It's the only **built-in aggregate** in the Java language — every other data structure (`ArrayList`, `HashMap`, `String`, even `StringBuilder`'s buffer) is implemented *on top of* arrays. Master arrays and you've mastered the memory shape under every container.

Arrays look simple — declare, allocate, index — but the depth is genuine. At the **language** layer, arrays have peculiarities found nowhere else: a `length` **field** (not a method!), **covariance** (`Object[] o = new String[3]` is legal and lets you blow up at runtime with `ArrayStoreException`), a literal syntax, and a parallel utility class (`java.util.Arrays`). At the **bytecode** layer, every element load and store has its own opcode family (`iaload`/`iastore` for `int[]`, `aaload`/`aastore` for reference arrays, `baload`/`bastore` for `byte[]`/`boolean[]`, etc.), every access carries an implicit **bounds check** (throws `ArrayIndexOutOfBoundsException`), and every reference store carries an implicit **array-store check** (throws `ArrayStoreException`). At the **memory** layer, an `int[1_000_000]` is ~4 MB **contiguous** in one allocation; an `Integer[1_000_000]` is ~20 MB **scattered** across 1,000,001 separate allocations — a 5× memory and ~10× cache penalty. At the **architecture** layer, the CPU's scaled-index addressing and stride-1 prefetcher make sequential primitive-array scans run at L1 throughput; the JIT's **bounds-check elimination** removes the per-access branch in idiomatic loops; row-major vs column-major access on a 2-D matrix changes performance by ~10× on large data. We'll cover every layer.

## Why Arrays Exist — The Only Built-In Aggregate

A variable holds **one** value (T02). An array holds **N** values of the same type, indexed `0..N-1`. The two features that make arrays special and irreplaceable:

1. **Contiguous storage** — all elements live in one allocation, adjacent in memory. The CPU's cache and prefetcher love this; primitive-array scans run at memory bandwidth.
2. **O(1) random access** — `arr[i]` is one address calculation (`base + i × sizeof(elem)`) and one memory load. Constant-time regardless of `i` or array size.

Compare:

| Structure | Memory shape | `arr[i]` cost |
|-----------|--------------|---------------|
| `int[]` | contiguous; 4 bytes/elem | O(1), one cache-line-friendly load |
| `LinkedList<Integer>` | scattered nodes, each holds value + 2 pointers | O(n) walk from head |
| `ArrayList<Integer>` | contiguous backing `Object[]`; each elem is a heap `Integer` reference | O(1) index, plus pointer-chase per elem |
| `HashMap<Integer,X>` | hash table on contiguous `Node[]` buckets | O(1) average via hash |

Every "fast" structure in `java.util` is either an array internally (`ArrayList`, `ArrayDeque`, `HashMap`, `PriorityQueue`) or a tree of small arrays. Arrays are the foundation.

```mermaid
flowchart TB
  Arr["int[5]"] --> Layout["header (16 bytes) | 4 | 4 | 4 | 4 | 4"]
  Layout --> Bytes["one contiguous 36-byte allocation"]
  Bytes --> CPU["CPU streams sequentially via prefetcher; cache-line friendly"]
```

## Declaring and Creating 1-D Arrays

### Declaration syntax

The Java-idiomatic form puts the brackets on the **type**:

```java
int[] nums;
String[] names;
```

A legacy C-style form puts brackets after the variable name:

```java
int nums[];                  // legal but discouraged
```

Both produce identical compiled code; the modern style is `int[] nums` because it reads "an array-of-int named nums," matching how generics later read (`List<Integer> nums`). The legacy form is the inheritance from C/C++.

You can even mix on the same line — **don't**:

```java
int[] a, b[];                 // a is int[]; b is int[][] — extremely confusing
```

### Creation with `new`

`new <type>[size]` allocates an array on the heap, **zero-initialising** every element to that type's default value:

```java
int[] zeros = new int[5];      // {0, 0, 0, 0, 0}
double[] amounts = new double[3];   // {0.0, 0.0, 0.0}
boolean[] flags = new boolean[2];   // {false, false}
String[] words = new String[4];     // {null, null, null, null}
```

| Element type | Default value |
|-------------|---------------|
| `byte`, `short`, `int`, `long` | `0` |
| `float`, `double` | `0.0` |
| `char` | `''` (the NUL character) |
| `boolean` | `false` |
| Any reference type | `null` |

```mermaid
flowchart TB
  New["new int[5]"] --> Alloc["allocate 16 bytes header + 5*4 bytes + padding"]
  Alloc --> Zero["zero every byte (JVM guarantee)"]
  Zero --> Ref["return reference to the array object"]
```

The zero-fill is a **JVM guarantee** — you never read garbage from a freshly-allocated array, unlike C. The JIT often implements the zero-fill via a `rep stosb`/`memset`-style instruction; for short arrays in stack-allocated escape-analyzed cases, it's a few `xor + store` instructions.

`size` may be any non-negative `int`. **Negative size** throws `NegativeArraySizeException`; **larger than `Integer.MAX_VALUE`** is a compile error (the size is an `int`); the practical maximum is also limited by the heap and by `-XX:MaxArrayLength` (~2³¹ - 8).

### Array literals

The literal syntax fills in elements directly. Two equivalent forms:

```java
int[] primes = {2, 3, 5, 7, 11};                  // declaration form (short)
int[] primes2 = new int[]{2, 3, 5, 7, 11};         // expression form (long)
```

The short form is only legal **at declaration** — you can't reassign with it:

```java
int[] primes;
primes = {2, 3, 5, 7, 11};                          // COMPILE ERROR
primes = new int[]{2, 3, 5, 7, 11};                  // OK — expression form
```

The expression form is what you need when passing a literal to a method:

```java
System.out.println(Arrays.toString(new int[]{1, 2, 3}));     // OK
System.out.println(Arrays.toString({1, 2, 3}));               // COMPILE ERROR
```

### Indexing — 0-based, half-open `[0, length)`

`arr[i]` accesses the `i`-th element, with `i ∈ [0, arr.length)`:

```java
int[] arr = {10, 20, 30};
arr[0]              // 10
arr[2]              // 30
arr[3]              // throws ArrayIndexOutOfBoundsException
arr[-1]             // throws ArrayIndexOutOfBoundsException
```

```mermaid
flowchart LR
  I0["arr[0] = 10"] --- I1["arr[1] = 20"] --- I2["arr[2] = 30"]
  Idx["valid indices: 0 .. length-1 = 0 .. 2"]
```

The half-open convention `[0, length)` is the universal rule across Java APIs (substring, list slicing, stream ranges, IntStream.range). Once internalised it stops you from writing `<=` in `for` loop conditions (the off-by-one bug from T09).

### The `length` field — *field*, not method

Every array has a public `final int` field named `length` that holds the element count. You read it without parentheses:

```java
int[] arr = new int[10];
arr.length          // 10
arr.length()        // COMPILE ERROR: 'length()' is not defined for int[]
```

> [!WARNING]
> Arrays use `arr.length` (field). Strings use `s.length()` (method). Collections use `c.size()` (method). Three different idioms for "how many elements?" — get them straight or expect compile errors and code-review nits forever.

The field is **immutable** at the language level: there's no `arr.length = 5` assignment, and the bytecode has no opcode for setting it. The length is decided at allocation and is fixed for the array's lifetime.

```mermaid
flowchart TB
  Field["arr.length — public final int field"]
  Bytecode["bytecode: arraylength opcode (single instruction)"]
  Set["no setter exists — length is fixed at allocation"]
  Field --> Bytecode
  Field --> Set
```

### Array covariance and `ArrayStoreException`

Java arrays are **covariant**: `String[]` is a subtype of `Object[]`. This lets you pass a `String[]` to a method expecting `Object[]`:

```java
void printAll(Object[] arr) {
    for (Object o : arr) System.out.println(o);
}

String[] names = {"a", "b"};
printAll(names);                             // OK — covariance lets this through
```

The catch: **you can store an `Object` into an `Object[]`** at the language level. If the runtime array is *actually* a `String[]`, the store fails:

```java
Object[] arr = new String[3];                // covariance: String[] IS-A Object[]
arr[0] = "hello";                            // OK — string into string array
arr[1] = new Integer(42);                    // throws ArrayStoreException at runtime
```

```mermaid
flowchart TB
  Decl["Object[] arr = new String[3]"]
  Decl --> StoreCheck{"aastore: is value an instance of array's actual element type?"}
  StoreCheck -- yes --> Ok["store; OK"]
  StoreCheck -- no --> Throw["throw ArrayStoreException"]
```

Every reference-array store carries an implicit **runtime type check** — the `aastore` bytecode opcode performs it. The check costs ~1-2 extra cycles per store on hot paths and is the price of array covariance. It can't be eliminated by the JIT in general because the actual element type is only known at runtime.

This is why **generics aren't covariant** at the language level: `List<String>` is **not** `List<Object>`. Generics erasure means there's no runtime type to check against, so the language refuses the conversion at compile time instead. Arrays are the historical odd-one-out (pre-generics design from Java 1.0).

> [!IMPORTANT]
> **Generic arrays don't fully exist.** `new T[10]` is a compile error inside a generic class; `new String[]` is fine. You can have a `T[]` field if you cast from `Object[]`, but it's the source of `unchecked` warnings. Prefer `ArrayList<T>` for generic collections.

### `Arrays.equals` vs `arr.equals`

`arr.equals(arr2)` is **reference equality** — inherited from `Object.equals` — and only returns true if both references point to the *same array object*:

```java
int[] a = {1, 2, 3};
int[] b = {1, 2, 3};
a.equals(b)                  // false — different array objects
Arrays.equals(a, b)          // true — element-wise comparison
```

> [!WARNING]
> Always use `Arrays.equals(a, b)` for value comparison; `a.equals(b)` on arrays is almost always a bug. (Some lint tools catch it; most don't.)

### `Arrays.asList(...)` — the two traps

`Arrays.asList` returns a **fixed-size** `List<T>` backed by the input array. Adding or removing elements throws `UnsupportedOperationException`:

```java
List<String> names = Arrays.asList("a", "b", "c");
names.set(0, "z");                           // OK — same array, slot 0 replaced
names.add("d");                              // throws UnsupportedOperationException
```

The first trap is autoboxing-blind: `Arrays.asList(int[])` does **not** give you a `List<Integer>`:

```java
int[] arr = {1, 2, 3};
List<int[]> wrapped = Arrays.asList(arr);     // length 1! the int[] is a SINGLE element
wrapped.size()                                 // 1
```

This is because `Arrays.asList` is varargs `<T> List<T> asList(T... a)`. `T` cannot be a primitive; it can be `int[]`. So a single `int[]` argument is treated as **one element of type `int[]`**, not as N `Integer` elements. Use `IntStream.of(arr).boxed().toList()` (Java 16+) or `Arrays.stream(arr).boxed().toList()`.

Second trap: a **boxed** wrapper array does what you'd expect:

```java
Integer[] boxed = {1, 2, 3};
List<Integer> list = Arrays.asList(boxed);    // size 3 — varargs expands the array
```

But you've already paid the autoboxing cost to build the `Integer[]` in the first place.

### `System.arraycopy` — bulk copy

For copying ranges between arrays, `System.arraycopy(src, srcPos, dst, dstPos, length)` is the canonical primitive:

```java
int[] src = {1, 2, 3, 4, 5};
int[] dst = new int[5];
System.arraycopy(src, 1, dst, 0, 3);          // dst = {2, 3, 4, 0, 0}
```

It's a native HotSpot intrinsic — lowers to `rep movsb` (Intel ERMS) or `movdqu`-loop on x86-64, and to `ldp.q`/`stp.q` 32-byte-pair loops on ARM64. It runs at memory bandwidth (T07's `arraycopy` deep dive).

`Arrays.copyOf` and `Arrays.copyOfRange` are convenience wrappers that allocate the destination first:

```java
int[] grown = Arrays.copyOf(arr, arr.length * 2);    // alloc + arraycopy + zero-pad
int[] slice = Arrays.copyOfRange(arr, 2, 5);          // alloc + arraycopy
```

### `clone()` — shallow copy

Every array has a `clone()` method (inherited from `Object`, with a covariant return type so `int[].clone()` returns `int[]`):

```java
int[] a = {1, 2, 3};
int[] b = a.clone();                          // {1, 2, 3} — independent copy
b[0] = 99;
System.out.println(a[0]);                     // 1 — a is unaffected
```

For a **1-D primitive array** `clone()` is exactly the same as `Arrays.copyOf(a, a.length)` — a single `arraycopy` of the elements.

For a **1-D reference array** `clone()` copies the references (not the referenced objects):

```java
String[] words = {"a", "b"};
String[] words2 = words.clone();              // words2 holds the same two String refs
```

For a **multi-D array** `clone()` is **shallow**: it copies the outer array, but the inner sub-arrays are **shared** between the original and the clone:

```java
int[][] grid = {{1,2},{3,4}};
int[][] copy = grid.clone();                  // outer array cloned; inner arrays SHARED
copy[0][0] = 99;
System.out.println(grid[0][0]);              // 99 — the inner int[] is shared!
```

```mermaid
flowchart TB
  G["grid (int[][]) — outer array"] --> R1G["row 0: int[2] {1,2}"]
  G --> R2G["row 1: int[2] {3,4}"]
  C["copy (int[][]) — outer cloned"] --> R1G
  C --> R2G
  Note["clone() copies only the outer references — inner arrays are SHARED"]
```

For a true deep copy of a 2-D array, clone each row individually:

```java
int[][] deep = new int[grid.length][];
for (int i = 0; i < grid.length; i++) deep[i] = grid[i].clone();
```

## Multi-Dimensional Arrays — "Arrays of Arrays"

**Java has no true multi-dimensional array.** `int[][]` is an `int[]` whose elements are themselves `int[]` references. The C/Fortran "one contiguous block of `R*C` ints" doesn't exist as a language construct (you can simulate it with `int[r*c]` and manual indexing — covered below).

### Declaration and creation

```java
int[][] grid = new int[3][4];                 // 3 rows, 4 columns, rectangular
```

This is **two-step** allocation under the hood:

1. Allocate the **outer** `int[][]` of length 3 (12-byte header + 4 byte length + 3 × 4-byte refs + padding = 32 bytes).
2. For each of the 3 outer slots, allocate a fresh **inner** `int[4]` (16 + 16 + 0 padding = 32 bytes each) and store its reference.

Result: **4 allocations** (one outer + three inner), **non-contiguous** memory layout, each row independently sized.

```mermaid
flowchart TB
  Outer["outer int[][] (length 3)"]
  Outer --> R0["int[4] {0,0,0,0}"]
  Outer --> R1["int[4] {0,0,0,0}"]
  Outer --> R2["int[4] {0,0,0,0}"]
  Note["four separate heap allocations; rows may be far apart in memory"]
```

### The "only outer" form for jagged arrays

You can create the outer array and leave the inner rows `null`, then fill them with arrays of **different lengths**:

```java
int[][] jagged = new int[3][];                // outer alloc only; rows are null
jagged[0] = new int[]{1};
jagged[1] = new int[]{1, 2};
jagged[2] = new int[]{1, 2, 3};
```

```mermaid
flowchart TB
  J["jagged (length 3)"]
  J --> JR0["int[1] {1}"]
  J --> JR1["int[2] {1,2}"]
  J --> JR2["int[3] {1,2,3}"]
```

Jagged arrays are useful when row lengths genuinely vary (e.g. a list of edges per vertex in a graph). They have the same byte cost as the rectangular form for the same total element count.

### Multi-D literal

```java
int[][] grid = {
    {1, 2, 3},
    {4, 5, 6},
    {7, 8, 9}
};
```

Same shape as the `new int[3][3]` form, populated. Inner braces are themselves array literals.

### Indexing

`grid[r][c]` is **two** indexed loads: first `grid[r]` to get the inner array reference (via `aaload`), then `inner[c]` to get the int element (via `iaload`).

```mermaid
flowchart LR
  Source["grid[r][c]"] --> Load1["aaload: outer[r] -> int[]"]
  Load1 --> Load2["iaload: inner[c] -> int"]
```

**Two memory loads per access** — vs **one** for a flat `int[r * cols + c]`. The JIT will inline both, but the cache footprint of multi-D is meaningfully larger.

### Row-major iteration is cache-friendly

```java
for (int r = 0; r < grid.length; r++) {
    for (int c = 0; c < grid[r].length; c++) {
        sum += grid[r][c];
    }
}
```

The **inner loop walks one row sequentially** — within a row, the `int`s are contiguous (each row is its own contiguous `int[]`), and the prefetcher streams them into L1. Good.

### Column-major iteration is cache-hostile on large matrices

```java
for (int c = 0; c < grid[0].length; c++) {
    for (int r = 0; r < grid.length; r++) {
        sum += grid[r][c];
    }
}
```

Each `grid[r][c]` is in a **different** row's `int[]` — potentially a different cache line on every access. For a 1000×1000 `int[][]`, the rows are likely 4 MB apart and column-major iteration **misses L1 on every access**.

```mermaid
flowchart TB
  RowMajor["row-major: arr[0][0], arr[0][1], arr[0][2], ... — one row, sequential"]
  RowMajor --> Cache1["all in same cache line; prefetcher streams"]
  ColMajor["column-major: arr[0][0], arr[1][0], arr[2][0], ... — different rows"]
  ColMajor --> Cache2["each access a different row's array; cold cache hits"]
```

We'll quantify this in the architecture section. The **rule of thumb**: iterate the rightmost (innermost) index in the inner loop.

### Flat `int[r * c]` for performance-critical 2-D

When you need maximum performance on a rectangular 2-D, flatten it:

```java
int rows = 1000, cols = 1000;
int[] flat = new int[rows * cols];
int get(int r, int c) { return flat[r * cols + c]; }
void set(int r, int c, int v) { flat[r * cols + c] = v; }
```

Trade-offs:

- **One** allocation instead of `rows + 1`.
- **One** contiguous block — best possible cache behaviour.
- **One** indexed load instead of two.
- The `r * cols + c` computation, which the JIT can simplify (induction variable in a `for (r) for (c) ... r * cols + c` becomes a running counter).
- Loses the "jagged" capability.
- Loses `grid[r].length` — you must track `rows` and `cols` separately.

For dense numerical work (matrices, image buffers, neural-net tensors), the flat form is universal. For sparse or jagged data, the array-of-arrays form is right.

### Three and more dimensions

```java
int[][][] cube = new int[3][4][5];            // 3 layers × 4 rows × 5 cols
```

Same recursive idea — an `int[3][4][5]` is an `int[][][]` of length 3, each element an `int[][]` of length 4, each element an `int[5]`. The compiler emits a single `multianewarray` bytecode opcode for rectangular multi-D creation; it allocates all the layers in one call.

## Memory Layer — Byte-Level Array Layout

### The Array Object Header

Every Java array is a heap-allocated object with an extended object header. The standard layout on a 64-bit HotSpot with compressed oops (the modern default):

```
offset 0  +-----------------------------+
          | mark word (8 bytes)         |  <- GC bits, hash, lock state
offset 8  +-----------------------------+
          | klass pointer (4 bytes,     |  <- compressed oops; 8 bytes without
          |  compressed)                |
offset 12 +-----------------------------+
          | length (4 bytes, int)       |  <- the .length field
offset 16 +-----------------------------+
          | element 0                   |
          | element 1                   |
          | ...                         |
          | element N-1                 |
          +-----------------------------+
          | padding to 8-byte alignment |
          +-----------------------------+
```

So the **fixed overhead** per array is **16 bytes** (12 header + 4 length, aligned to 8). The element area is `N * sizeof(elemtype)`, rounded up to the next 8-byte boundary.

### Per-type element sizes

| Element type | Bytes per element | `int[10]` total | `T[10]` total (compressed oops) |
|-------------|------------------:|----------------:|----:|
| `boolean` | 1 (one byte per bool in HotSpot, NOT one bit!) | 16 + 10 + 6 pad = 32 | — |
| `byte` | 1 | 32 | — |
| `short`, `char` | 2 | 16 + 20 + 4 pad = 40 | — |
| `int`, `float` | 4 | 16 + 40 + 0 pad = 56 | — |
| `long`, `double` | 8 | 16 + 80 + 0 pad = 96 | — |
| reference (compressed) | 4 | — | 16 + 40 + 0 pad = 56 |
| reference (uncompressed, `-XX:-UseCompressedOops`) | 8 | — | 16 + 80 + 0 pad = 96 |

> [!IMPORTANT]
> **`boolean[]` is *not* a bit-array.** Each `boolean` occupies 1 full byte in HotSpot — for memory-density-critical bitmaps, use `BitSet` or a `long[]` with manual bit-shifting.

### `int[1_000_000]` vs `Integer[1_000_000]`

```
int[1_000_000]:
  16 (header + length) + 4_000_000 (elements) + 0 pad
  = ~4 MB, ONE allocation, contiguous

Integer[1_000_000]:
  16 (header + length) + 4_000_000 (references, compressed) + 0 pad
  = 4 MB for the array itself
  + 1_000_000 × 16 (each Integer: 12 hdr + 4 value + 0 pad = 16 bytes)
  = + 16 MB for the Integer objects, SCATTERED across the heap
  = ~20 MB total, 1_000_001 allocations
```

```mermaid
flowchart TB
  IntArr["int[1M] — one 4MB contiguous block"]
  IntArr --> CacheGood["cache: stride-1, prefetcher engages, L1 throughput"]
  IntegerArr["Integer[1M] — 4MB of refs + 1M scattered Integer objs"]
  IntegerArr --> CacheBad["cache: each elem is a pointer-chase to a different cache line"]
  CacheGood --- vs["vs"] --- CacheBad
```

**5× memory** and roughly **10× worse cache behaviour**. This is why every performance-sensitive Java codebase uses primitive arrays over wrapper arrays where it can.

### Element-load and element-store opcodes — per-type

The JVM has a **dedicated opcode per element type** for array reads and writes. The naming pattern is `<type>aload` for reads and `<type>astore` for writes:

| Bytecode | Element type read/written | Reads stack | Pushes/pops |
|----------|---------------------------|-------------|-------------|
| `iaload` / `iastore` | `int` (and `byte`, `short`, `char` after auto-promote) | `int[]`, `int` (index) | int / pops `int` value |
| `laload` / `lastore` | `long` | `long[]`, `int` | long |
| `faload` / `fastore` | `float` | `float[]`, `int` | float |
| `daload` / `dastore` | `double` | `double[]`, `int` | double |
| `aaload` / `aastore` | reference (any object) | `Object[]`, `int` | reference |
| `baload` / `bastore` | `boolean` or `byte` | `byte[]`/`boolean[]`, `int` | int |
| `caload` / `castore` | `char` | `char[]`, `int` | int |
| `saload` / `sastore` | `short` | `short[]`, `int` | int |

Plus three array-administration opcodes:

| Bytecode | Role |
|----------|------|
| `newarray` | allocate a primitive array (`new int[size]`, `new boolean[size]`, etc.) |
| `anewarray` | allocate a reference array (`new String[size]`) |
| `multianewarray` | allocate a rectangular multi-D array (`new int[3][4][5]`) |
| `arraylength` | read `arr.length` — single opcode |

Each load/store reads the array reference and the index from the operand stack, performs the access, and (for loads) pushes the element. Each access carries an implicit check:

1. **Null check**: if the array reference is `null`, throw `NullPointerException`.
2. **Bounds check**: if the index is `< 0` or `>= length`, throw `ArrayIndexOutOfBoundsException`.
3. **Store check** (`aastore` only): if storing a reference, verify it's assignable to the array's actual element type; if not, throw `ArrayStoreException`.

```mermaid
flowchart TB
  Op["iaload"] --> Null{"arr == null?"}
  Null -- yes --> NPE["throw NPE"]
  Null -- no --> Bounds{"0 <= idx < length?"}
  Bounds -- no --> AIOOBE["throw ArrayIndexOutOfBoundsException"]
  Bounds -- yes --> Load["push arr[idx] to stack"]
```

The bounds check is what range-check elimination (T09) targets — when the JIT proves the loop invariant `0 ≤ i < length`, it omits the check.

### Worked `javap -c` for a 1-D scan

Source:

```java
int sum(int[] arr) {
    int s = 0;
    for (int i = 0; i < arr.length; i++) s += arr[i];
    return s;
}
```

Bytecode:

```
 0: iconst_0
 1: istore_2                    // s = 0
 2: iconst_0
 3: istore_3                    // i = 0
 4: iload_3                     // load i
 5: aload_1                     // load arr
 6: arraylength                  // arr.length
 7: if_icmpge   23              // i >= arr.length? exit
10: iload_2                     // load s
11: aload_1                     // load arr
12: iload_3                     // load i
13: iaload                      // arr[i] (implicit bounds + null check)
14: iadd                        // s + arr[i]
15: istore_2                    // s = ...
16: iinc       3, 1             // i++
19: goto       4                // backward jump (loop close)
23: iload_2
24: ireturn
```

Every iteration: one `arraylength` (often hoisted by the JIT via LICM — T09), one `iaload` (with implicit bounds check, eliminated by RCE — T09), one `iinc`, one `if_icmpge`, one `goto`. After JIT: ~3 native instructions per element, often 8 elements per AVX2 SIMD instruction.

### Worked `javap` for a 2-D scan — two-level indexing

Source:

```java
int sumGrid(int[][] grid) {
    int s = 0;
    for (int r = 0; r < grid.length; r++) {
        for (int c = 0; c < grid[r].length; c++) {
            s += grid[r][c];
        }
    }
    return s;
}
```

Bytecode for the inner-body element load:

```
... (inner loop body) ...
   aload_1               // load grid
   iload_3               // load r
   aaload                // grid[r] : int[]
   iload   4             // load c
   iaload                // (int[])[c] : int
   iadd                  // s += ...
   ...
```

Two indexed loads per element. The `aaload` reads a reference (the inner `int[]`); the `iaload` reads the int. Both carry their bounds checks; the JIT can eliminate both if the loop bounds use the same `.length` fields.

### Multi-D allocation — `multianewarray`

For `new int[3][4]`, javac emits a single bytecode:

```
   iconst_3
   iconst_4
   multianewarray   [[I, 2     // type descriptor "[[I" (int[][]), dimensions count 2
```

This one opcode does all four allocations (one outer + three inner) and links them together. For `new int[3][]` (outer only), javac emits `anewarray [I` instead — one allocation, inner slots `null`.

### Lifetime and GC

An array is a regular heap object: it stays alive as long as some reachable reference holds it; the GC reclaims it when nothing references it. A multi-D array's inner sub-arrays are referenced *by the outer array*, so they stay alive as long as the outer does — until you `null` out a slot:

```java
int[][] grid = new int[1000][1000];           // ~4 MB total
grid[0] = null;                                // row 0's int[1000] becomes garbage
// ~4 KB freed at next GC
```

For very large arrays you may want to consider `-XX:+UseG1GC` or `-XX:+UseZGC` (the latter handles multi-GB arrays without long pauses); the default G1 already handles arrays well up to many GB.

## Architecture Layer — CPU, Cache, JIT

### Scaled-index addressing — array access is free address math

x86-64 and ARM64 both have **scaled-index addressing modes** that compute `base + index × scale` in the address-generation unit, **in parallel** with the ALU. So `arr[i]` for an `int[]` (scale=4) is:

```asm
; x86-64 (rdx = arr_base, rdi = i)
mov     eax, [rdx + rdi*4]              ; one instruction; *4 is free
```

```asm
; ARM64 (x3 = arr_base, w0 = i)
ldr     w4, [x3, w0, sxtw #2]           ; one instruction; #2 = log2(4), sxtw promotes
```

```mermaid
flowchart TB
  Src["arr[i] (int[])"] --> X86["x86-64: mov eax, [rdx + rdi*4]"]
  Src --> ARM["ARM64: ldr w4, [x3, w0, sxtw #2]"]
  Note["the *4 and sxtw #2 are free — computed in the address unit"]
```

For `long[]` use scale 8; for `byte[]` use scale 1; for `double[]` use 8. The CPU handles all of them. **The `*sizeof(elem)` is invisible to the throughput count** — it's not a multiply, it's a shift inside the load unit.

### Bounds-Check Elimination (recap from T09)

The naive lowering of `arr[i]` would emit:

```asm
        cmp     edi, [rdx - 4]          ; arr.length sits 4 bytes before element 0
        jae     .throw_aioobe           ; >= length unsigned -> throw
        mov     eax, [rdx + rdi*4]      ; safe to access
```

The JIT proves `0 ≤ i < arr.length` for idiomatic `for (int i = 0; i < arr.length; i++)` and **deletes the `cmp` + `jae`** entirely. The loop body becomes a single load. This is the difference between Java being competitive with C on numeric loops vs being 3-5× slower.

```mermaid
flowchart TB
  Naive["mov eax, [rdx + rdi*4]   AFTER   cmp + jae bounds-check"]
  AfterRCE["mov eax, [rdx + rdi*4]   (no bounds check)"]
  Naive -. JIT eliminates .-> AfterRCE
```

### Cache lines and the prefetcher

A modern x86-64 CPU has **64-byte L1 cache lines** — 16 ints, 8 longs, 8 doubles, or 32 shorts per line. When you read `arr[0]`, the cache pulls in `arr[0..15]` for free. When you read `arr[1]`, it's already there.

The **hardware prefetcher** detects stride-1 access after ~3-4 misses and starts loading **future** cache lines speculatively. By the time the loop iterates past element 15 of the first line, the line containing `arr[16..31]` is already arriving in L1.

```mermaid
flowchart TB
  Iter1["read arr[0..15] — line N"]
  Iter1 -.-> Prefetch["prefetcher: 'stride-1 detected; fetch line N+1, N+2'"]
  Iter2["read arr[16..31] — line N+1 (already in L1)"]
  Iter2 -.-> PF2["prefetcher: continue fetching N+3, N+4"]
```

Result: **sequential primitive-array scans run at L1 throughput** (~4 ints/cycle on Skylake-era), which is many times faster than DRAM bandwidth would permit if you missed L1 on every access.

### `int[]` vs `Integer[]` — the cache disaster

Walk `int[1_000_000]` sequentially: 1,000,000 / 16 = **62,500 cache lines**, all stride-1, all prefetcher-friendly.

Walk `Integer[1_000_000]` sequentially: 62,500 lines for the **reference** array, but each reference points to a **separate 16-byte `Integer` object** somewhere in the heap. The prefetcher cannot follow pointers (it only knows strides), so each `Integer` access is a **cold cache load** — potentially ~100 ns to L3, ~300 ns to DRAM. **1,000,000 cold cache misses** for the loop body, vs ~62,500 warm hits for `int[]`.

For a sum loop, this is the difference between ~1 ms (`int[]`) and ~50–100 ms (`Integer[]`) on the same hardware. **50–100×.**

### Row-major vs column-major — the 2-D matrix case

For a 1000×1000 `int[][]`:

- **Row-major** (`for r: for c: grid[r][c]`): inner loop walks one row's `int[1000]` sequentially. Each row is contiguous; prefetcher streams. 1000 cache-warm rows × 1000 iterations = 1 ms total.
- **Column-major** (`for c: for r: grid[r][c]`): each access reads a different row's `int[]`. The 1000 rows are scattered across ~4 MB of heap. Each access is potentially a cache miss to L2 or L3. ~10–50 ms total.

```mermaid
flowchart TB
  RM["row-major: 1000 rows × 1000 sequential reads = ~1 ms"]
  CM["col-major: 1,000,000 scattered reads = ~10-50 ms"]
  Bench["benchmarked difference: ~10x"]
  RM --- vs --- CM
  vs --> Bench
```

**Iterate the rightmost index in the innermost loop.** That's the universal rule for cache-friendly multi-D loops in any row-major language (Java, C, Rust, Go). Fortran and MATLAB are column-major, so the rule inverts there.

### `Arrays.sort` — two different algorithms

`Arrays.sort` is overloaded per element type, and the algorithm differs:

- **`Arrays.sort(int[])`** (and `long[]`, `float[]`, `double[]`, `char[]`, `short[]`, `byte[]`) uses **dual-pivot quicksort** (Yaroslavskiy's variant, 2009). In-place, O(n log n) average, O(n²) worst case (rare with three-way partition); faster than classical Hoare quicksort by ~20% on random data because the dual pivots reduce comparisons.
- **`Arrays.sort(Object[])`** (and `Arrays.sort(List)`, `Collections.sort`) uses **Timsort** (Tim Peters, 2002 — same as Python's `sorted`). Stable (equal elements keep their original order), O(n log n) worst case, exploits pre-existing sorted runs, allocates a temp array (O(n) extra space).

Why the split? Primitive arrays don't have equal-but-distinguishable elements, so stability is meaningless; quicksort's in-place nature wins. Object arrays often have stability requirements (sort by name, preserve original order for equal names) and may already be partially sorted (Timsort exploits this).

```mermaid
flowchart TB
  Sort["Arrays.sort"] --> Prim["primitive arr -> dual-pivot quicksort (in-place, O(n log n) avg)"]
  Sort --> Obj["Object arr -> Timsort (stable, O(n log n) worst, O(n) extra space)"]
```

`Arrays.parallelSort(...)` uses a **parallel merge-sort** based on the fork/join framework — splits the array, sorts pieces on different threads, merges. Wall-clock improvement on large arrays (~4 cores → ~3× faster on 1M elements); not worth the overhead for small arrays (the JDK uses a small-input threshold).

### `System.arraycopy` as a HotSpot intrinsic

`System.arraycopy(src, sp, dst, dp, len)` is **not** a regular Java method call. HotSpot intercepts it and emits **native bulk-copy** code:

- **x86-64**: `rep movsb` (Intel ERMS-optimised) or an AVX2 unrolled loop using `vmovdqu` 32-byte loads/stores. Runs at **L1 cache bandwidth** for in-cache data, **memory bandwidth** for out-of-cache.
- **ARM64**: paired `ldp.q`/`stp.q` (32-byte loads/stores) in an unrolled loop, or `dc zva` (data-cache zero-by-VA) when zeroing.

A 1 GB copy on modern hardware takes ~100 ms (~10 GB/s memory bandwidth). No Java loop you write by hand will match this — always use `System.arraycopy` for bulk copy.

```mermaid
flowchart TB
  Call["System.arraycopy(src, sp, dst, dp, len)"]
  Call --> HotSpot["HotSpot intrinsic: skip the Java call"]
  HotSpot --> Native["emit rep movsb / vmovdqu loop (x86) or ldp.q (ARM)"]
  Native --> MB["~memory bandwidth (~10 GB/s)"]
```

### False sharing on parallel array writes

When multiple threads write to **different slots of the same array** in adjacent cache lines, the CPU treats it as one shared line and bounces ownership between cores — **false sharing**. Each write is delayed by tens to hundreds of cycles. For `int[]` shared across threads:

```java
int[] counters = new int[NUM_THREADS];      // each thread writes its own slot
```

— **disastrous**: all 16 slots fit in one 64-byte line, and the line ping-pongs between cores. Fix by padding each counter to its own cache line, or using `LongAdder` (which handles striping internally). Full coverage in L3/C01 (concurrency).

### Escape Analysis on short-lived arrays

`int[] temp = new int[16]` inside a method that doesn't pass `temp` to an un-inlined caller: HotSpot's **scalar replacement** can lift the array elements into stack-allocated slots or registers, **eliminating the heap allocation entirely**. This is the same EA mechanism we saw for `StringBuilder` (T07) and Iterator (T09). For small, bounded, non-escaping arrays it works; for arrays of unbounded or runtime-determined size it usually doesn't.

## Common Mistakes

> [!WARNING]
> **The classic array bug catalogue.** These come up in code review constantly.

### `arr.length` vs `arr.length()`

`arr.length` is a field. Writing `arr.length()` is a compile error specific to arrays — Strings have `.length()`, collections have `.size()`, arrays have `.length`. Memorise the three.

### 0-based vs 1-based off-by-one

```java
for (int i = 1; i <= arr.length; i++) arr[i] = ...;     // both ends off by one!
```

The right form is `for (int i = 0; i < arr.length; i++)`. The half-open `[0, length)` convention is universal in Java APIs.

### `arr.equals(arr2)` is reference equality

```java
int[] a = {1, 2, 3};
int[] b = {1, 2, 3};
a.equals(b)              // false! reference equality
Arrays.equals(a, b)       // true
```

`Object.equals` defaults to `==`; arrays don't override it. Always use `Arrays.equals` or `Arrays.deepEquals`.

### `Arrays.asList(int[])` returns a `List<int[]>` of size 1

```java
int[] arr = {1, 2, 3};
List<int[]> wrong = Arrays.asList(arr);     // size 1!
```

Varargs `<T>` cannot bind to a primitive type. Use `IntStream.of(arr).boxed().toList()` to get a `List<Integer>`.

### Shallow `clone()` on 2-D arrays

Covered earlier — `grid.clone()` shares inner rows. For a real deep copy of a `T[][]`, clone every inner row. For a `T[][][]`, recursively.

### Modifying an array after passing to a method

Pass-by-value-of-reference (T02): a method receives a **copy of the reference**, not a copy of the array. Mutations inside the method are visible to the caller.

```java
void zero(int[] arr) { for (int i = 0; i < arr.length; i++) arr[i] = 0; }

int[] data = {1, 2, 3};
zero(data);
// data is now {0, 0, 0}
```

This is correct Java — but readers from Python or JS may expect "by value" semantics. Defensive copy (`int[] safe = arr.clone()`) if you don't want callees mutating.

### `ArrayStoreException` from generic-array confusion

```java
Object[] arr = new String[3];
arr[0] = 42;                              // throws ArrayStoreException
```

Array covariance + reference-type stores. The runtime check fires. Use generics (`List<String>`) for type-safe collections.

### Allocating in a hot loop

```java
for (int i = 0; i < n; i++) {
    int[] temp = new int[16];             // allocates every iteration!
    process(temp);
}
```

Hoist the allocation out of the loop, or reuse with `Arrays.fill(temp, 0)` if the contents don't need to outlive the loop. The JIT's EA *may* eliminate this if `temp` doesn't escape, but don't rely on it.

### `int[]` to `List<Integer>` autoboxing cost

```java
int[] arr = {1, 2, 3, ..., 1_000_000};
List<Integer> list = Arrays.stream(arr).boxed().collect(Collectors.toList());
```

5× memory blow-up plus 1 million allocations. Stay in `int[]` (or `IntStream`) if you can; box only at the boundary where you need `List<Integer>`.

### Forgetting that an `Object[]` may not be what its declared type says

```java
String[] names = new String[3];
Object[] o = names;
o[0] = new Integer(42);                  // throws ArrayStoreException
```

Covered above — `Object[] o` doesn't mean "an array that holds anything"; it means "a reference to some array, whose actual element type is determined at allocation time."

### Multi-D arrays "must" be rectangular

False — `int[3][]` is legal and leaves rows `null` for you to fill with different lengths (jagged). Only the *rectangular* form `int[3][4]` allocates all rows up front.

### `Arrays.copyOf` truncation vs extension

```java
int[] a = {1, 2, 3};
int[] b = Arrays.copyOf(a, 5);            // {1, 2, 3, 0, 0}  — padded with default
int[] c = Arrays.copyOf(a, 2);            // {1, 2}           — truncated
```

The behaviour is "exactly newLen elements; pad or truncate the source." Useful when growing an `ArrayList`-style buffer (`Arrays.copyOf(arr, arr.length * 2)`).

> [!INTERVIEW]
> Arrays are a perennial Java interview topic. Common angles:
>
> 1. **What's the difference between `arr.length` and `arr.length()`?** Arrays have a `length` field; Strings have a `length()` method; collections have `size()`.
> 2. **Why is `Arrays.asList(int[])` size 1?** Varargs can't bind `T` to a primitive; it binds `T = int[]`, treating the whole array as one element. Use `IntStream.of(...).boxed().toList()`.
> 3. **What's array covariance?** `T[]` is a subtype of `S[]` if `T extends S`. Lets you pass `String[]` to `Object[]` params. Cost: runtime `ArrayStoreException` on incompatible reference stores.
> 4. **Why aren't generics covariant?** Erasure — no runtime element type to check; the language enforces invariance at compile time instead.
> 5. **How is `int[][]` laid out in memory?** Outer `int[][]` of references + N separately-allocated inner `int[]`s. Non-contiguous; row-major iteration is cache-friendly.
> 6. **What's the byte size of `int[10]`?** 16 (header + length) + 40 (elements) + 0 padding = 56 bytes.
> 7. **What's the byte size of `Integer[10]`?** 16 + 40 (refs) + ... + ~160 (10 Integers) = ~200 bytes scattered (depending on cache).
> 8. **What's `iaload` and what does it cost?** Bytecode for `int[]` element read. Implicit null + bounds check. JIT eliminates the bounds check in idiomatic loops (RCE).
> 9. **Which sort does `Arrays.sort(int[])` use?** Dual-pivot quicksort (Yaroslavskiy), in-place, O(n log n) avg.
> 10. **Which sort does `Arrays.sort(Object[])` use?** Timsort. Stable. O(n log n) worst.
> 11. **How fast is `System.arraycopy`?** HotSpot intrinsic; runs at memory bandwidth (`rep movsb` / `vmovdqu` on x86; `ldp.q` on ARM).
> 12. **Why is `int[]` 50× faster than `Integer[]` in a tight sum loop?** Cache packing + prefetcher: `int[]` is contiguous (16/line, stride-1); `Integer[]` is pointer-per-element with scattered boxes (cold miss per element).

## Practice

1. **JOL layout dump.** Use the Java Object Layout (JOL) library to print `int[10]`, `Integer[10]`, and `Object[10]` layouts. Confirm 16-byte header + 4×N elements + padding.
2. **`int[]` vs `Integer[]` memory.** Measure heap before and after allocating `int[1_000_000]` and `Integer[1_000_000]` (with all `Integer` values created via `new Integer(i)` to disable caching). Confirm ~4 MB vs ~20 MB.
3. **`int[]` vs `Integer[]` performance.** Sum 100M elements both ways. Measure nanos. Confirm 30–50× difference.
4. **Row-major vs column-major.** Sum a 2000×2000 `int[][]` row-major then column-major. Measure. Confirm ~10× difference.
5. **Flat array as 2-D.** Reimplement the same matrix sum using `int[2000*2000]` and `idx = r*cols + c`. Measure. Should be ~as fast as row-major `int[][]` (maybe slightly faster due to one fewer indirection).
6. **`javap -c` 1-D sum.** Disassemble the sum loop. Find `arraylength`, `iaload`, `iinc`, the backward `goto`.
7. **`javap -c` 2-D access.** Disassemble `grid[r][c]`. Find the `aaload` followed by `iaload`.
8. **`javap -c` multi-D creation.** Disassemble `new int[3][4]`. Find the `multianewarray` opcode.
9. **Range-check elimination.** Run `for (int i = 0; i < arr.length; i++) arr[i] = i;` with `-XX:+PrintAssembly` (needs `hsdis`). Confirm no `cmp arr_length, idx` bounds check inside the inner loop. Then rewrite as `for (int i = 0; i < computeLen(arr); i++)` where `computeLen` is in another class; observe the check re-appearing.
10. **ArrayStoreException reproduction.** Reproduce the `Object[] o = new String[3]; o[0] = 42;` example. Trace the JVM error message; identify the array's actual element type.
11. **Shallow `clone()` 2-D trap.** Clone a 2-D `int[][]`. Modify a deeply-nested element. Confirm the original sees the change. Fix with per-row clone.
12. **`Arrays.asList(int[])` trap.** Reproduce the `size() == 1` confusion. Compare to `Arrays.asList(Integer[])` (size N) and `Arrays.asList(1, 2, 3)` (size 3).
13. **`Arrays.sort` algorithm observation.** Sort an `int[1M]` and an `Integer[1M]` with random data. Measure. Sort a *partially-sorted* `Integer[]`. Confirm Timsort exploits the runs (much faster than random); dual-pivot doesn't get the same speedup on partially-sorted `int[]`.
14. **`System.arraycopy` intrinsic.** Run `-XX:+PrintIntrinsics`. Run a loop that does `System.arraycopy`. Confirm it's intrinsified. Then write a manual copy loop; benchmark; observe the manual loop is significantly slower (no SIMD/ERMS).
15. **Auto-vectorisation on `int[]`.** Sum `int[1M]` with `-XX:+PrintAssembly`. Find `vpaddd` (AVX2) or `add v.4s` (NEON). Switch off with `-XX:-UseSuperWord`; measure throughput drop.
16. **`boolean[]` byte cost.** Allocate `boolean[1_000_000]`; measure heap. Confirm it's ~1 MB (one byte per bool), not ~128 KB (one bit per bool). Compare to `BitSet`.
17. **Explain it back.** Trace `int[][] g = new int[3][4]; g[1][2] = 42;` from source through (a) `multianewarray` bytecode, (b) the four heap allocations, (c) the `aaload` + `iastore` for the assignment, (d) the JIT's two scaled-index `mov`s, (e) the cache-line(s) touched.

## Recap

You should now be able to:

- Recognise an **array** as Java's only built-in aggregate: fixed-size, contiguous, indexed, O(1) random access, the foundation under every container in `java.util`.
- Declare arrays with the idiomatic `int[] nums` syntax (not C-style `int nums[]`), allocate with `new int[size]` (zero-initialised) or with an array literal `{1, 2, 3}` (declaration form only) / `new int[]{1, 2, 3}` (expression form).
- Recall the **default values** per element type — 0 for numeric, `` for `char`, `false` for `boolean`, `null` for references.
- Apply the **half-open `[0, length)`** indexing convention; recognise `length` as a **field** (not method), final and decided at allocation.
- Recognise **array covariance** — `String[]` IS-A `Object[]` — and its runtime cost: every reference store via `aastore` carries an implicit type check that throws `ArrayStoreException` on a mismatch.
- Use the **`java.util.Arrays`** utility class: `toString`/`deepToString` for printing, `equals`/`deepEquals` for value comparison (vs `arr.equals` which is reference equality!), `hashCode` for use as Map keys, `fill` to set, `sort`/`parallelSort` to order, `binarySearch` to query a sorted array (O(log n)), `copyOf`/`copyOfRange` to slice, `stream` for stream operations, `asList` to view as a fixed-size List.
- Apply the **`Arrays.asList(int[])` trap** workaround — use `IntStream.of(arr).boxed().toList()` to get a `List<Integer>`.
- Use **`System.arraycopy`** for bulk copy (memory-bandwidth speed via HotSpot intrinsic), `arr.clone()` for a 1-D shallow copy, and explicit per-row cloning for a deep copy of multi-D arrays.
- Understand that **Java has no true multi-dimensional array** — `int[][]` is an `int[]` of `int[]`s. Use `new int[r][c]` for rectangular (allocated all at once via `multianewarray`); use `new int[r][]` for jagged (rows allocated separately).
- Trace **byte-level array layout**: 16-byte header (12 object header + 4 length, padded to 8) + N × sizeof(elem) elements + padding to 8-byte alignment.
- Quantify **`int[1M]` ≈ 4 MB contiguous** vs **`Integer[1M]` ≈ 20 MB scattered** (5× memory, ~10× cache penalty) and use primitive arrays for performance-critical paths.
- Recall the **per-type element-load/store opcodes**: `iaload`/`iastore`, `laload`/`lastore`, `faload`, `daload`, `aaload`/`aastore` (with the store check), `baload`, `caload`, `saload`, plus `arraylength`, `newarray`, `anewarray`, `multianewarray`.
- Explain the **three implicit checks** every array access performs: null check (NPE), bounds check (`ArrayIndexOutOfBoundsException`), and (for `aastore`) array-store check (`ArrayStoreException`).
- Predict the **JIT's native-code shape**: scaled-index addressing `[base + idx*N]` on x86-64 (`mov eax, [rdx+rdi*4]`) / ARM64 (`ldr w4, [x3, w0, sxtw #2]`); bounds-check elimination removes the per-access guard in idiomatic `for (int i = 0; i < arr.length; i++)` loops.
- Explain **cache and prefetcher** behaviour on sequential 1-D scans: 64-byte cache lines (16 ints/line); stride-1 detection after 3-4 misses; prefetcher streams future lines into L1; loop runs at L1 throughput.
- Explain why **row-major iteration** of `int[][]` is fast and **column-major** is ~10× slower — each column-major access lands in a different row's `int[]`, scattered across the heap, cold cache.
- Recall that **`Arrays.sort(int[])` uses dual-pivot quicksort** (Yaroslavskiy, in-place, O(n log n) avg) and **`Arrays.sort(Object[])` uses Timsort** (stable, O(n log n) worst, O(n) extra space, exploits pre-existing sorted runs).
- Recall that **`System.arraycopy` is a HotSpot intrinsic** lowering to `rep movsb`/`vmovdqu` on x86-64 or `ldp.q`/`stp.q` on ARM64, running at memory bandwidth.
- Avoid the **common traps**: `length` vs `length()`, 0-vs-1-based off-by-one, `arr.equals` (reference!) vs `Arrays.equals` (value), `Arrays.asList(int[])` returning a 1-element `List<int[]>`, shallow `clone()` sharing inner rows of a multi-D array, pass-by-reference letting callees mutate, `ArrayStoreException` from covariant-array misuse, allocation in hot loops, `int[]`→`List<Integer>` autobox cost, `boolean[]` being byte-per-element not bit-per-element.
