istio-circuit-breaker/ — Mesh-level circuit breaking & fault injection

examples/k8s-manifests/istio-circuit-breaker

Implements the circuit breaker and bulkhead resilience patterns at the service-mesh layer — no Java library, no application redeploy.

Backing topics: L5/C02/T14 (resilience patterns) and the Netflix case study, L5/C12/T01 (Hystrix → Envoy/mesh circuit breaking).

Files#

File Role
destinationrule.yaml The circuit breaker: connectionPool (bulkhead / load shedding) + outlierDetection (eject unhealthy hosts). Apply this.
virtualservice.yaml Optional fault injection (delays + 503s, header-gated) to TEST that the breaker and your client timeouts actually work.

How the two halves work together#

                 connectionPool (bulkhead)          outlierDetection (breaker)
client ──► Envoy ──► caps concurrent conns/   ──► strips out hosts returning
   ▲                  requests; fast-fails 503      5xx; probes them back in
   │                  when caps are hit               │
   └─────────────────── 503 fast-fail ◄───────────────┘
  1. connectionPool bounds how much in-flight work can pile up against the dependency. Hitting a cap returns 503 immediately (fail fast) instead of queueing requests until everything times out (fail slow → latency collapse, the classic cascading-failure trigger).
  2. outlierDetection watches per-host error rates and ejects a backend that keeps returning 5xx, then re-admits it after baseEjectionTime. That is the circuit "opening" and "half-opening" — done by the sidecar, per host.

maxEjectionPercent and minHealthPercent stop the breaker from ejecting the entire pool (an open circuit that can never close).

From Hystrix to the mesh (L5/C12/T01)#

Netflix's Hystrix put the circuit breaker inside the JVM (a library wrapping every remote call). The mesh approach moves the identical pattern into the Envoy sidecar: language-agnostic, uniform across services, and tunable without a code change or redeploy. Hystrix is now in maintenance mode precisely because mesh/Envoy (and, in-process, Resilience4j) superseded it. Use mesh breaking for cross-service calls; use Resilience4j in-process when you need a fallback method or finer-grained, business-aware control.

Testing it (fault injection)#

bash
kubectl apply -f destinationrule.yaml      # the breaker
kubectl apply -f virtualservice.yaml       # optional fault injection

# Drive faulted traffic and watch the breaker trip. Only x-chaos:on is faulted.
for i in $(seq 1 50); do
  curl -s -H 'x-chaos: on' -o /dev/null -w '%{http_code}\n' http://url-shortener/
done | sort | uniq -c        # expect a mix of 200 / 503 / slow responses

# Inspect Envoy's circuit-breaker + outlier stats on the sidecar:
kubectl -n url-shortener exec deploy/url-shortener -c istio-proxy -- \
  pilot-agent request GET stats | grep -E 'outlier|circuit_breakers|pending'

Remove virtualservice.yaml after testing — it is a chaos tool, not a steady-state config.

Prerequisites#

  • Istio mesh installed; url-shortener namespace in the mesh.
  • The Deployment/Service from ../spring-boot-3-deployment/.

destinationrule.yaml#

yaml
# =============================================================================
# Istio DestinationRule — MESH-LEVEL CIRCUIT BREAKER
# -----------------------------------------------------------------------------
# Backing topics:
#   - L5/C02/T14  Resilience patterns (circuit breaker, bulkhead, timeouts).
#   - L5/C12/T01  Netflix case study (Hystrix popularized the in-process
#                 circuit breaker; a service mesh moves the same pattern OUT of
#                 your code and into the sidecar — no library, no redeploy).
#
# Two cooperating mechanisms make up the breaker:
#   1. connectionPool  — BULKHEAD: caps concurrent connections/requests so a
#                        slow dependency can't exhaust all your resources.
#                        When caps are hit, Envoy fast-fails with 503 instead
#                        of queueing forever (fail fast > fail slow).
#   2. outlierDetection — the BREAKER itself: ejects individual backend hosts
#                        that return errors, then probes them back in.
#
# API: networking.istio.io/v1 (GA, Istio 1.22+). Use v1beta1 on older meshes.
# =============================================================================
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: url-shortener-circuit-breaker
  namespace: url-shortener
spec:
  host: url-shortener        # The Service these policies protect.
  trafficPolicy:
    # -------------------------------------------------------------------------
    # CONNECTION POOL (bulkhead / load shedding)
    # -------------------------------------------------------------------------
    connectionPool:
      tcp:
        maxConnections: 100        # Max TCP connections Envoy opens to all
                                   # endpoints of this host combined. Beyond
                                   # this, new connections wait/fail — prevents
                                   # a connection flood to a struggling backend.
        connectTimeout: 3s         # Give up establishing a TCP connection after
                                   # 3s instead of hanging.
        tcpKeepalive:
          time: 7200s
          interval: 75s
      http:
        http1MaxPendingRequests: 50   # Queue depth for requests waiting on a
                                      # connection. Small + bounded = fail fast
                                      # under overload rather than building an
                                      # unbounded backlog (the latency-collapse
                                      # failure mode).
        http2MaxRequests: 100         # Max concurrent requests (HTTP/2 streams)
                                      # across all hosts.
        maxRequestsPerConnection: 100 # Recycle a connection after N requests
                                      # (mitigates connection-affinity skew; 0 =
                                      # unlimited).
        maxRetries: 3                 # Cap retries IN FLIGHT at once, so a retry
                                      # storm can't amplify load on a sick
                                      # backend (retries make outages worse).
    # -------------------------------------------------------------------------
    # OUTLIER DETECTION (the circuit breaker: eject unhealthy hosts)
    # -------------------------------------------------------------------------
    outlierDetection:
      # A host that returns this many consecutive 5xx (gateway errors) is
      # ejected from the load-balancing pool — Envoy stops sending it traffic.
      consecutive5xxErrors: 5
      # Also trip on consecutive gateway errors (502/503/504) specifically.
      consecutiveGatewayErrors: 5
      interval: 10s              # How often Envoy sweeps hosts for ejection.
      baseEjectionTime: 30s      # Initial eviction duration. Each repeat
                                 # ejection multiplies this (30s, 60s, 90s...),
                                 # so flapping hosts stay out longer.
      maxEjectionPercent: 50     # Never eject more than half the pool at once —
                                 # protects against ejecting ALL hosts and taking
                                 # the service fully down (the "open circuit that
                                 # never closes" trap).
      minHealthPercent: 40       # If healthy hosts drop below 40%, disable
                                 # outlier detection (better to load-balance over
                                 # everything than to have nothing to route to).

virtualservice.yaml#

yaml
# =============================================================================
# Istio VirtualService — FAULT INJECTION for testing resilience (OPTIONAL)
# -----------------------------------------------------------------------------
# This is a CHAOS-TESTING tool, not something you run in steady-state prod.
# Istio can synthetically inject delays and HTTP errors at the mesh layer so you
# can verify that:
#   - the circuit breaker in destinationrule.yaml actually trips,
#   - your client's retries/timeouts behave (and don't retry-storm),
#   - upstream callers degrade gracefully (fallbacks, cached responses).
#
# Ties to L5/C02/T14 (resilience) and the Netflix Chaos Monkey lineage
# (L5/C12/T01): deliberately break things in a controlled way to prove the
# system survives. Gate it behind a header so ONLY test traffic is faulted.
#
# API: networking.istio.io/v1 (GA). Use v1beta1 on older meshes.
# =============================================================================
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: url-shortener-fault-injection
  namespace: url-shortener
spec:
  hosts:
    - url-shortener
  http:
    # -------------------------------------------------------------------------
    # FAULTED ROUTE: only requests carrying `x-chaos: on` are degraded. This
    # keeps real users unaffected while you run a controlled experiment.
    # -------------------------------------------------------------------------
    - name: chaos-testing
      match:
        - headers:
            x-chaos:
              exact: "on"
      fault:
        delay:
          percentage:
            value: 50.0      # Add latency to 50% of matched requests...
          fixedDelay: 5s     # ...a 5s delay (should trip client timeouts).
        abort:
          percentage:
            value: 20.0      # Abort 20% of matched requests...
          httpStatus: 503    # ...with 503 (feeds outlierDetection's 5xx count).
      route:
        - destination:
            host: url-shortener
    # -------------------------------------------------------------------------
    # NORMAL ROUTE: everything without the chaos header passes through clean.
    # -------------------------------------------------------------------------
    - name: passthrough
      route:
        - destination:
            host: url-shortener
